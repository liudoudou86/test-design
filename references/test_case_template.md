## 填写指南

### ID 命名规则
- 格式：`TC-{模块缩写}-{3位序号}`
- 示例：`TC-LOGIN-001`, `TC-REG-002`
- 建议与 TestOutline 的测试点 ID 保持一致的模块缩写

### 测试类型
| 类型 | 说明 |
|------|------|
| 功能 | 业务逻辑验证 |
| UI/UX | 界面与交互体验 |
| 兼容性 | 多浏览器/设备/OS |
| 性能 | 响应时间、并发、吞吐量 |
| 安全 | 注入、越权、XSS、CSRF |
| 无障碍 | WCAG标准符合性 |

### 优先级定义
- P0：阻塞上线，必须通过
- P1：重要功能，建议通过
- P2：辅助功能，可后续迭代

### 前置条件
- 对于需要特定状态或数据的用例，描述前提
- 如果不需要特定前置条件，填"N/A"

### 测试步骤
- 关键步骤详细描述
- 常规步骤可简化
- 步骤间用分号或换行分隔

### 预期结果
- 必须可验证
- 不要写"功能正常"之类模糊描述
- 示例：返回HTTP 200；页面显示"注册成功"；数据库新增一条记录

## 测试用例生成方法速查

### 输入型功能（如表单/API参数）
优先使用等价类划分法 + 边界值分析法
- 等价类：有效值、无效值
- 边界值：最小值-1、最小值、正常值、最大值、最大值+1

### 流程型功能（如购物/审批流程）
优先使用场景法
- 基本流：完整的成功路径
- 备选流：每一步的异常分支
- 扩展流：非核心功能的附加路径

### 复杂逻辑判断（如折扣规则/权限控制）
优先使用因果图/决策表法
- 列出所有条件和动作
- 生成条件组合
- 识别冗余和冲突

### AI相关功能（如推荐/风控）
参考 `references/test_strategy.md` 中的特殊方法

### 综合场景
组合使用多种方法确保穷举
